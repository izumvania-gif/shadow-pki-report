# Shadow PKI Report — требования и план разработки PoC

*Приложение к странице PoC. Владелец: Иван Черников*

*Редакция 2. Учтены правки по итогам [оценки](assessment.md). Что именно изменилось — в [журнале изменений](#6-журнал-изменений).*

**Принцип сбора:** только публичные реестры — логи Certificate Transparency и публичные DNS-записи. Инструмент не обращается к инфраструктуре компании, по которой строится отчёт: не устанавливает соединений с её хостами, не выполняет TLS-хендшейк, не сканирует порты. DNS-запросы уходят к резолверам, а не к целевым системам.

**Канал доставки отчёта:** существующие контакты. Массовой холодной рассылки нет — отчёт передаётся компаниям, с которыми у нас уже есть отношения, через менеджера или партнёрский канал.

**Формат:** команда 3 человека, 2 дня.

---

## 1. Источник данных и его границы

Лог Certificate Transparency хранит сертификат целиком, поэтому по домену доступны: издатель, полный список имён из SAN, срок действия, серийный номер, алгоритм подписи, тип и длина ключа, отпечаток сертификата и отпечаток публичного ключа. Публичный DNS дополняет это тем, какие из найденных имён резолвятся и куда указывают.

Из этого следуют две вещи, которые определяют формулировку отчёта.

**Мы видим факт выпуска, а не факт использования.** Работает ли сервис на найденном имени, какая на нём версия протокола и предъявляет ли он именно этот сертификат — по реестрам неизвестно. Поэтому в отчёте везде «сертификат выпущен на такое-то имя», и нигде «сертификат используется». Иначе на первой же встрече администратор скажет, что этот хост давно выключен, и под сомнение попадёт весь документ.

**Внутренний контур невидим.** Самоподписанные сертификаты и сертификаты внутренних УЦ в CT не публикуются в принципе. Отчёт покрывает только то, что выпущено публично доверенными УЦ.

Оба ограничения выносятся в отчёт отдельным разделом о методологии, а не прячутся. На встрече второе ограничение работает в нашу пользу: то, что видно снаружи, — заведомо меньшая часть картины, а невидимое как раз и закрывается Рутокен CLM.

Предмет отчёта, соответственно, — не состояние инфраструктуры, а дисциплина выпуска сертификатов: сколько их выпускается на домены компании, через какие УЦ, кто это делает и что остаётся неперевыпущенным.

## 2. Общие требования

### 2.1. Сбор данных

| Требование | Описание |
|---|---|
| Вход | Один корневой домен. Опционально — список дополнительных доменов компании и список известных заказчику имён для сверки. |
| Основной источник | Логи Certificate Transparency: все сертификаты, выпущенные на домен и его поддомены. |
| Разворачивание имён | Из каждого сертификата извлекается полный список SAN и сводится в общий перечень имён с указанием, каким сертификатом имя покрыто. |
| DNS | По найденным именам запрашиваются публичные записи: резолвится ли имя, куда указывает, есть ли CNAME. Имя без адреса — отдельная категория находки. |
| Извлекаемые поля | Subject, Issuer, полный SAN, notBefore, notAfter, серийный номер, алгоритм подписи, тип и длина ключа, отпечаток сертификата, отпечаток публичного ключа. |
| Отпечаток ключа | Обязателен — на нём строится правило «один публичный ключ на нескольких несвязанных именах». |
| Дедупликация | Предсертификаты и соответствующие им конечные сертификаты схлопываются в одну запись, иначе объём удваивается и отчёт врёт по количеству. |
| Горизонт выборки | Задаётся явно, по умолчанию 24 месяца по `notBefore`. Значение фиксируется в отчёте. Без ограничения выборка забивается историей десятилетней давности. |
| Персональные данные | Поля Subject, способные содержать ФИО и личные адреса (`emailAddress`, `CN` у сертификатов на физлиц), не сохраняются в рабочий набор и не попадают ни в отчёт, ни в экспорт. См. п. 2.8. |
| Проверка отзыва | Опционально. Запрос уходит к OCSP-респондеру УЦ, а не к системам компании, поэтому принцип сбора не нарушается. Берём, если останется время. |

### 2.2. Семантика данных: линия сертификата

Раздел добавлен по итогам оценки. **Определения из этой таблицы фиксируются в первый час работы, вместе с форматом данных между этапами 1 и 2, и до написания первой строки кода.**

Схлопывания предсертификатов недостаточно. При коротком сроке жизни публичных сертификатов и автоматическом продлении CT-лог по одному имени за два года содержит десятки последовательных выпусков. Без правильной группировки:

- счётчик «найдено N сертификатов» завышается на порядок, и отчёт врёт в первой же строке сводки;
- правило «истёк и не перевыпущен» срабатывает на каждом историческом сертификате в цепочке, то есть почти на всех;
- «несколько разных УЦ на один домен» ложно срабатывает на любой миграции между УЦ, случившейся когда угодно в прошлом.

| Понятие | Определение |
|---|---|
| **Линия сертификата** | Хронологическая цепочка выпусков на один и тот же набор SAN. Ключ группировки — нормализованный набор имён. |
| **Актуальный сертификат линии** | Последний по `notBefore` сертификат в линии. |
| **Найдено сертификатов** | Число **линий**. Общее число записей в CT выводится отдельной метрикой «выпусков за период» и не подменяет собой первую. |
| **«Истёк и не перевыпущен»** | Актуальный сертификат линии истёк, и более нового в линии нет. Срабатывает только при этом условии. |
| **«Несколько УЦ на домен»** | Разные УЦ имеют **одновременно действующие** сертификаты. Смена УЦ в прошлом находкой не является. |
| **Ритм продления** | Медианный интервал между выпусками в линии. Отличает автоматизированный процесс от ручного — нужен для расчёта трудозатрат в п. 2.5. |

### 2.3. Фильтрация чужого

Часть найденного компании не принадлежит: сертификаты CDN и облачных провайдеров, сторонние сервисы на её домене, партнёрские и клиентские поддомены, следы давно закрытых проектов. Если это не отсечь, отчёт разваливается на первом же вопросе.

Оценка относит этот пункт к ядру продукта: всё остальное в системе тривиально, а определение принадлежности — единственная нетривиальная задача проекта. Бюджет времени планируется соответственно.

Способ фильтрации определяется по факту, а не проектируется заранее:

1. На этапе 0 продакт прогоняет собственные домены группы, где эталон известен, и 2–3 внешних домена, и вручную разбирает сырую выгрузку.
2. По результатам формулируется, что является мусором и по каким признакам оно отличимо.
3. Правила фиксируются в конфиге, а не в коде, и уточняются по мере прогона следующих доменов.

**Разметка трёхуровневая, а не бинарная:**

| Уровень | Что означает | Что с ним происходит |
|---|---|---|
| `own` | Принадлежность подтверждена правилом | Проходит в отчёт автоматически |
| `foreign` | Атрибутировано внешнему владельцу или провайдеру | Исключается автоматически, с сохранением причины |
| `unknown` | Правило не сработало ни в одну сторону | Выносится на экран ручного подтверждения |

Это резко сокращает ручную работу: оператор разбирает только третью категорию, а не всю выгрузку.

Требования к реализации:

- отфильтрованный объект не удаляется, а остаётся с пометкой причины исключения, чтобы можно было проверить, не выкинули ли лишнего;
- фильтр отключается одним переключателем, сырая выгрузка доступна для просмотра;
- перед формированием финального PDF предусмотрен экран ручного подтверждения, где сотрудник разбирает категорию `unknown` и убирает явно чужие записи;
- **решения оператора сохраняются** — какая запись, какое решение, по какому домену. Это обучающая выборка для будущей автоматизации фильтра. Без накопления с первого дня автоматизировать будет не на чем.

Ручное подтверждение на PoC — не костыль, а осознанное решение: автоматизировать фильтр можно только после того, как на живых данных станет понятно, что именно фильтровать.

### 2.4. Движок правил

Ключевой переиспользуемый актив прототипа. Правила описываются декларативно (YAML или JSON), а не хардкодом, чтобы тот же набор без переписывания применялся к результатам агентского и безагентского сканирования в Рутокен CLM.

Структура правила: идентификатор, условие, уровень критичности, формулировка находки для отчёта, рекомендация по устранению.

Все правила применяются к **линиям** сертификатов в терминах п. 2.2, а не к отдельным записям CT.

**Базовый набор — находки:**

- актуальный сертификат линии истёк и не был перевыпущен;
- истекает менее чем через 7 / 30 дней;
- длина ключа RSA менее 2048;
- алгоритм подписи SHA-1 или слабее;
- wildcard-сертификат покрывает большое число имён;
- один публичный ключ обнаружен в сертификатах на несвязанные имена;
- имя резолвится, но актуальный сертификат линии истёк;
- имя из SAN не резолвится вообще — забытый ресурс, на который продолжают выпускаться сертификаты;
- имена, характерные для тестовых, отладочных и служебных сред, засветившиеся в публичном логе;
- **выпуск не атрибутирован** — источник выпуска не удалось связать ни с инфраструктурным провайдером, ни с известным процессом компании.

Последние три пункта — самые убедительные на встрече: компания не собиралась публиковать эти имена, но выпуск сертификата попадает в лог автоматически, и убрать его оттуда уже нельзя.

**Информационные наблюдения — выводятся в сводку как факт, но находкой не считаются:**

- выпуск, атрибутируемый инфраструктурному провайдеру (CDN, хостинг, PaaS, ACME в составе платформы);
- число задействованных УЦ с одновременно действующими сертификатами;
- медианный ритм продления по линиям.

**Почему правила про УЦ переформулированы.** В первой редакции ACME-выпуск трактовался как признак того, что команды получают сертификаты в обход ИТ. На современном внешнем периметре это норма, встроенная в хостинг-панели, CDN, Kubernetes-контроллеры и PaaS: компания с сотней сертификатов от бесплатного ACME-УЦ, скорее всего, имеет не проблему дисциплины, а автоматизированный процесс — ровно тот, к которому CLM её и ведёт. Предъявить такое как нарушение — показать непонимание её инфраструктуры на первой же встрече. Поэтому находкой считается не бесплатный УЦ сам по себе, а **невозможность атрибутировать выпуск**. Мультивендорность по той же причине переведена в наблюдение: у крупной компании она часто осознанна — разные УЦ для разных контуров, резервный УЦ на случай отзыва, УЦ, навязанный CDN-провайдером.

**Тон формулировок.** Обвинительных конструкций («в обход ИТ», «нарушение») в отчёте нет. Нейтральные: «выпуск вне единого процесса», «источник выпуска не идентифицирован». Отчёт констатирует, выводы делает читатель.

Формулировки находок и рекомендаций пишет продакт до старта разработки, а не команда во время хакатона. Это дешёвая часть, которая сильнее всего влияет на то, как отчёт читается заказчиком.

### 2.5. Отчёт

**Формат:** PDF. Структура:

1. Сводка на одну страницу для руководителя: сколько имён и линий сертификатов найдено, сколько УЦ задействовано, сколько проблем по уровням критичности.
2. Методология: использованы только публичные реестры, обращений к инфраструктуре компании не производилось, данные отражают факт выпуска сертификатов, внутренний контур в выборку не попадает, горизонт выборки — N месяцев.
3. Перечень имён с признаком резолвинга.
4. Таблица сертификатов.
5. Находки, сгруппированные по критичности, с рекомендациями.
6. Оценка объёма ручной работы на сопровождение найденного количества сертификатов.
7. Переход: публичные реестры показывают меньшую часть картины, внутренний контур извне не наблюдаем и обычно на порядок объёмнее.

**Расчётная модель трудозатрат (п. 6).** Оценка отмечает это как самую конвертирующую часть отчёта, поэтому пункт разворачивается в расчёт, а не абзац: найдено N линий на внешнем периметре → при отраслевом соотношении внутренних и внешних сертификатов 1:X это ориентировочно N·X сертификатов всего → при текущем сроке жизни это M операций продления в год → это H человеко-часов. Коэффициенты X и трудоёмкость одной операции задаются в конфиге и подкрепляются ссылкой на отраслевое исследование, а не берутся из воздуха. Раздел 7 опирается на этот же расчёт: переход к внутреннему контуру должен быть подкреплён цифрой, а не метафорой.

**Политика по «чистому» отчёту.** Если находок нет, отчёт заказчику не отправляется: документ со словами «у вас всё в порядке» работает против нас. Такой результат остаётся внутри как отрицательный кейс для калибровки.

**Дополнительно:**

- Машиночитаемый экспорт (JSON или CSV) — задел под импорт в реестр Рутокен CLM. Ограничения по персональным данным из п. 2.8 действуют и на экспорт.
- Вариант отчёта без нашего брендинга для передачи партнёру — если останется время.

### 2.6. Интерфейс

- Веб-форма: ввод домена, запуск, статус выполнения, экран ручного подтверждения выгрузки, ссылка на готовый отчёт.
- История запусков со ссылками на прошлые отчёты.
- Простая авторизация, инструмент внутренний.
- Требование к юзабилити: продакт или сотрудник партнёрского отдела получает отчёт самостоятельно, без обращения к разработчику. Если для запуска нужна консоль — задача не выполнена.

### 2.7. Нефункциональные требования

| Параметр | Значение |
|---|---|
| Время генерации | До 5 минут на домен. |
| Взаимодействие с целевой инфраструктурой | Отсутствует. Соблюдение проверяется не только на уровне архитектуры, но и **тестом в CI**: сервис поднимается с перехватом исходящих соединений, разрешён только список адресов источников (API CT-логов, DNS-резолверы, при включённой опции — OCSP-респондеры). Любое соединение вне списка роняет сборку. Ключевое требование продукта не должно держаться на договорённости. |
| Лимиты источников | Соблюдение ограничений публичных CT-сервисов, корректная обработка ответов о превышении лимита без падения задачи. |
| Аудит | Логирование каждого запуска: кто инициировал, какой домен, когда. |
| Воспроизводимость | Результаты сохраняются так, чтобы повторный запуск через месяц давал сопоставимый diff. |

### 2.8. Персональные данные и тон

**Персональные данные.** В полях Subject сертификатов, особенно OV и EV, встречаются имена и адреса сотрудников. Правило простое и реализуется на этапе нормализации, а не на этапе вёрстки отчёта:

- в рабочий набор из Subject попадают только организационные поля: `O`, `OU`, `C`, `L`, `ST`;
- поле `emailAddress` и `CN`, не являющийся доменным именем, отбрасываются при разборе сертификата;
- ограничение действует одинаково на PDF, на машиночитаемый экспорт и на экран ручного подтверждения;
- WHOIS и подобные источники, где персональные данные ожидаемы, не используются вовсе.

**Тон.** Даже юридически чистый отчёт может прочитаться как давление: «мы изучили вашу инфраструктуру и нашли у вас проблемы». Дистанция между «вот что видно о вас в публичных реестрах» и «мы вас проверили» — вопрос трёх формулировок, и она определяет, будет встреча или жалоба. Формулировки пишет продакт на этапе 0.

**Юридическая рамка.** Вопрос массовой холодной рассылки снят: отчёт передаётся компаниям из существующей базы контактов, через менеджера или партнёрский канал. Остаётся проверить у юристов две вещи, обе узкие: правомерность сбора по публичным реестрам (CT публичен по замыслу, DNS — публичная система, активного взаимодействия нет) и корректность формы передачи документа компании, с которой отношения уже есть.

### 2.9. Явно вне скоупа

- Любое обращение к хостам компании: сканирование портов, TLS-хендшейк, проверка версий протокола, полноты цепочки и соответствия предъявляемого сертификата найденному.
- Самоподписанные сертификаты и сертификаты внутренних УЦ — вне зоны видимости источника.
- Внутренняя сеть, агенты, доступ в инфраструктуру.
- Автоматическое продление и ротация.
- Интеграция с реестром Рутокен CLM — следующий шаг, если гипотезы подтвердятся.
- Публичный self-service для внешних пользователей.
- Массовая холодная рассылка отчётов.

## 3. План разработки

### Этап 0. Подготовка продакта (до старта, время команды не занимает)

**Этап 0 — жёсткий гейт.** Если он не закрыт полностью, старт переносится. Иначе хакатон уйдёт на разбор сырых данных вместо разработки, и это главный организационный риск плана.

Два разных списка доменов, у них разные задачи:

**А. Калибровочные — собственные домены группы.** Корневые домены Рутокен, Гардант и Актив (`rutoken.ru`, `guardant.ru`, `aktiv-company.ru` — точный перечень фиксирует продакт). По ним известен эталонный реестр, поэтому именно на них считаются полнота и ложные срабатывания — единственная честная техническая метрика PoC. Дополнительно они дают готовую обучающую выборку для фильтра: заранее известно, что из найденного относится к CDN, что к подрядчикам, что к партнёрам. Ограничений на прогон нет, гонять можно сколько угодно.

**Чего калибровка на своих доменах не даёт.** Актив — вендор PKI, его собственная дисциплина выпуска заведомо лучше средней по целевому сегменту. Прогон по своим доменам проверяет, что инструмент работает точно, но **не проверяет продуктовую гипотезу** «компания не знает своих сертификатов». Малое число находок на своих доменах — не признак плохого инструмента. Для проверки продуктовой гипотезы нужна компания из базы знакомых, готовая сверить находки со своим учётом; договориться об этом — задача этапа 0.

**Б. Демонстрационные — 10 компаний целевого сегмента из существующей базы контактов.** Вручную проверено, что находки на них есть. На них проверяется, что отчёт читается и что находки содержательны.

Остальное по этапу:

- Прогнаны калибровочные домены и 2–3 демонстрационных, разобрана сырая выгрузка, сформулированы первые правила фильтрации и трёхуровневой разметки.
- Написаны формулировки правил, находок и рекомендаций — в нейтральном тоне, по п. 2.4.
- Готов макет отчёта: структура разделов и тексты-заглушки.
- Заданы коэффициенты расчётной модели трудозатрат и найдена ссылка на отраслевое исследование по соотношению внутренних и внешних сертификатов.
- Получены ключи доступа к источникам CT, проверены лимиты, подтверждена доступность из нашей сети.
- Пройдена проверка у юристов по двум узким вопросам из п. 2.8.
- Согласована минимум одна компания из базы, готовая сверить находки со своим реестром.

### Этап 1. Выгрузка и нормализация (день 1, первая половина)

Получение сертификатов по домену, разбор полей, схлопывание предсертификатов, **сборка линий по п. 2.2**, разворачивание SAN в перечень имён, DNS-резолвинг, отбрасывание персональных полей Subject по п. 2.8. Вывод — JSON.

Готово, когда: по домену получен перечень имён и линий сертификатов со всеми полями из п. 2.1, включая отпечаток публичного ключа.

**Точка синхронизации:** в первый час работы фиксируются две вещи — формат данных между этапом 1 и этапом 2 и **семантика линии сертификата из п. 2.2**. Это единственная жёсткая зависимость в плане, и закрыть её нужно до того, как кто-то напишет первую строчку. Без второй половины разработчик 1 отдаст плоский список записей CT, разработчик 2 построит на нём правила, оба будут правы, а числа в отчёте — нет.

### Этап 2. Движок правил и фильтрация (день 1, вторая половина)

Загрузка правил из конфига, применение к собранным данным, выдача находок с уровнями критичности и информационных наблюдений. Отдельным конфигом — правила трёхуровневой разметки принадлежности, с сохранением исключённых записей, причины исключения и решений оператора.

Готово, когда: на реальных данных срабатывают все базовые правила, на калибровочных доменах посчитаны полнота и ложные срабатывания, продакт разобрал ложные срабатывания и уточнил фильтр.

### Этап 3. Генерация отчёта (день 2, первая половина)

Отчёт делается как **HTML-шаблон с печатью в PDF средствами браузера** — это основной путь, а не запасной. Он быстрее, лучше выглядит и правится продактом без разработчика, в отличие от любой PDF-библиотеки. Плюс машиночитаемый экспорт и экран ручного подтверждения перед выгрузкой.

Готово, когда: получен отчёт по реальному домену, который можно показать не-инженеру.

### Этап 4. Веб-интерфейс (день 2, первая половина, параллельно этапу 3)

Форма запуска, очередь задач, статус, история отчётов.

Готово, когда: продакт запускает отчёт сам, разработчик не участвует.

### Этап 5. Прогон и защита (день 2, вторая половина)

Прогон по калибровочным и 10 демонстрационным доменам, разбор ложных срабатываний, уточнение фильтра и правил, подготовка демонстрации, фиксация результатов по критериям приёмки контура A.

Цифры, которые должны быть на руках к защите:

| Метрика | Где считается |
|---|---|
| Полнота: доля имён из эталонного реестра, найденных инструментом | Калибровочные домены |
| Ложные срабатывания: доля находок, отклонённых при разборе | Калибровочные домены |
| Доля записей, снятых оператором на экране подтверждения | Все домены |
| Время генерации отчёта | Все домены |
| Число находок по уровням критичности | Демонстрационные домены |

### Распределение работ

| Роль | Зона |
|---|---|
| Разработчик 1 | Этап 1 — выгрузка, нормализация, сборка линий, DNS |
| Разработчик 2 | Этапы 2 и 3 — правила, фильтрация, отчёт |
| Разработчик 3 | Этап 4 — интерфейс, очередь, хранилище, тест изоляции сети для CI |
| Продакт | Этап 0 целиком, тексты, ручная валидация находок и фильтра, отбор доменов, подготовка защиты |

### Если формат хакатона трёхдневный

Прототип укладывается в два дня. Третий день имеет смысл потратить на **diff по времени**: повторная выгрузка и сравнение — какие сертификаты появились, какие исчезли, какие не были перевыпущены.

Оценка ставит diff выше экспорта в реестр Рутокен CLM, и по двум причинам. Первая: diff превращает разовый отчёт в повторяющийся повод для контакта — «с прошлого отчёта у вас появилось 12 новых сертификатов, 3 не были перевыпущены», — а контакт конвертирует не с первого касания. Вторая: он почти ничего не стоит, так как требование воспроизводимости уже в НФТ и структура данных под diff всё равно закладывается. Экспорт в CLM — интеграционная задача, которая имеет смысл после подтверждения гипотез, и она никуда не денется.

Альтернатива, которая тоже лучше экспорта, — отдать день команде с более рискованной задачей. Технической неопределённости здесь немного, и удерживать под прототип три дня разработки оснований нет.

### Если прототип делает выделенная команда

По флоу регламента через технического директора план растягивается на 2–3 недели с добавлением: регулярной выгрузки с diff по расписанию, интеграции экспорта с реестром Рутокен CLM, режима самообслуживания для партнёров и разграничения доступа. Этапы и их последовательность не меняются.

**Оговорка по срокам:** оценка в 2–3 недели реалистична, пока фильтр принадлежности остаётся ручным. Его автоматизация на накопленной статистике — отдельная работа сопоставимого объёма, и её нельзя записывать строкой в общий список. Накопление обучающей выборки начинается с первого прогона (п. 2.3), автоматизация имеет смысл после 20–30 разобранных доменов.

## 4. Риски

| Риск | Реакция |
|---|---|
| **Этап 0 не закрыт к старту, хакатон уходит в разбор данных** | Этап 0 — жёсткий гейт. Нет доменов, написанных формулировок и коэффициентов модели — старт переносится. |
| **Числа в сводке завышены из-за неверной группировки выпусков** | Семантика линии сертификата фиксируется в первый час, до кода (п. 2.2). |
| **Ложные срабатывания на CDN и ACME дискредитируют отчёт на встрече** | Разделение находок и информационных наблюдений (п. 2.4), трёхуровневая разметка, ручное подтверждение, вычитка первых отчётов продактом. |
| Лимиты публичных CT-сервисов при массовых запросах | Ключи и запасной источник получены на этапе 0. При исчерпании — работа по заранее выгруженному срезу. |
| Фильтрация чужого не поддаётся автоматизации за отведённое время | Ожидаемый исход. Экран ручного подтверждения закрывает это на PoC, автоматизация переносится на следующий шаг, обучающая выборка копится с первого прогона. |
| Отобранные домены оказались «чистыми», находок нет | Проверить 10 демонстрационных доменов вручную на этапе 0. Демонстрация на компании без единой проблемы — провал защиты при полностью работающем коде. |
| Отчёт без находок выдаёт заказчику справку «у вас порядок» | Такой отчёт не отправляется (п. 2.5), остаётся внутри как отрицательный кейс. |
| Возражение «этот хост давно выключен, отчёт неверный» | Формулировки строятся вокруг факта выпуска, а не использования. Методология вынесена в отчёт отдельным разделом. |
| Возражение «это повторение бесплатных публичных сервисов» | Данные действительно публичны — и именно поэтому их никто не собирает и не интерпретирует. Продаём не выгрузку, а её прочтение в отраслевом контексте и оценку стоимости сопровождения. Проговорить на защите первым, не дожидаясь вопроса. |
| Отчёт прочитан как давление | Нейтральный тон (п. 2.8), доставка через существующий контакт, а не рассылкой. |
| **Продуктовая гипотеза остаётся непроверенной, PoC закрывают как «код работает»** | Критерии приёмки разведены на контур A (день 2) и контур B (4–6 недель) — см. [постановку PoC](poc.md#критерии-приёмки-poc). |
| Инструмент остаётся жить как разовая демонстрация | Владелец сопровождения назначается сразу, вместе с планом diff-режима. |

*Жирным выделены риски, добавленные во второй редакции по итогам оценки.*

## 5. Открытые вопросы

- Отраслевой источник для коэффициента соотношения внутренних и внешних сертификатов — нужен до этапа 0, иначе расчёт трудозатрат не на что опереть.
- Какая компания из базы согласится сверить находки со своим реестром и на каких условиях.
- Нужна ли контрольная группа для проверки продуктовой гипотезы: раз рассылки нет и все адресаты — знакомые компании, отклик смещён вверх сам по себе. Чтобы утверждение «отчёт конвертирует лучше обычного письма» что-то значило, часть базы должна получить обычное письмо. Решение за продактом.
