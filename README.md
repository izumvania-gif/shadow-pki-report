# Shadow PKI Report

**Внешний аудит TLS-сертификатов по одному доменному имени — без обращения к инфраструктуре компании.**

Сервис по корневому домену собирает из публичных реестров картину выпущенных на компанию TLS-сертификатов и формирует PDF-отчёт о проблемах: просроченные и не перевыпущенные, истекающие в ближайшие недели, выпущенные в обход централизованного процесса, со слабой криптографией, wildcard-сертификаты и переиспользованные ключи на неучтённых именах.

Отчёт используется как повод для входа в диалог с ЛПР и как воронка в основной продукт — Рутокен CLM.

## Ключевой принцип: только публичные реестры

Инструмент **не обращается к инфраструктуре компании**, по которой строится отчёт:

- не устанавливает соединений с её хостами;
- не выполняет TLS-хендшейк;
- не сканирует порты;
- DNS-запросы уходят к публичным резолверам, а не к целевым системам.

Источники данных — **логи Certificate Transparency** и **публичные DNS-записи**.

Требование проверяется на уровне архитектуры и закреплено тестом в CI: сервис поднимается с перехватом исходящих соединений, разрешён только список адресов источников, любое соединение вне списка роняет сборку.

**Канал доставки отчёта — существующие контакты.** Массовой холодной рассылки нет: отчёт передаётся компаниям, с которыми у нас уже есть отношения, через менеджера или партнёрский канал.

## Что из этого следует для формулировок отчёта

Два ограничения источника определяют, как пишется каждая строка отчёта:

1. **Видно факт выпуска, а не факт использования.** Работает ли сервис на найденном имени и предъявляет ли он именно этот сертификат — по реестрам неизвестно. Поэтому везде «сертификат выпущен на имя», нигде — «сертификат используется».
2. **Внутренний контур невидим.** Самоподписанные сертификаты и сертификаты внутренних УЦ в CT не публикуются. Отчёт покрывает только выпущенное публично доверенными УЦ.

Оба ограничения выносятся в отчёт отдельным разделом о методологии, а не скрываются.

Предмет отчёта — **не состояние инфраструктуры, а дисциплина выпуска сертификатов**: сколько их выпускается на домены компании, через какие УЦ и что остаётся неперевыпущенным.

## Как это работает (целевой сценарий)

```
корневой домен
      │
      ▼
[1] выгрузка из CT-логов ──── все сертификаты на домен и поддомены
      │
      ▼
[2] SAN + сборка линий ────── перечень имён + цепочки выпусков
      │
      ▼
[3] публичный DNS ─────────── резолвится / куда указывает / висит без адреса
      │
      ▼
[4] разметка принадлежности ─ own / foreign / unknown
      │                        (unknown → экран ручного подтверждения)
      ▼
[5] движок правил ─────────── находки с уровнями критичности
      │
      ▼
[6] PDF-отчёт + JSON/CSV ──── сводка, методология, таблицы, находки, рекомендации
```

## Компоненты

| Компонент | Назначение |
|---|---|
| **Коллектор** | Выгрузка из CT, разбор полей, схлопывание предсертификатов, сборка линий, разворачивание SAN, DNS-резолвинг, отбрасывание персональных полей Subject. Вывод — JSON. |
| **Фильтр принадлежности** | Трёхуровневая разметка `own` / `foreign` / `unknown`. Правила в конфиге. Исключённое не удаляется, а помечается причиной; решения оператора сохраняются как обучающая выборка. |
| **Движок правил** | Декларативные правила (YAML/JSON): идентификатор, условие, критичность, формулировка находки, рекомендация. **Ключевой переиспользуемый актив** — тот же набор применяется к результатам сканирования в Рутокен CLM. |
| **Генератор отчёта** | PDF по шаблону + машиночитаемый экспорт (JSON/CSV). |
| **Веб-интерфейс** | Форма запуска, очередь, статус, экран ручного подтверждения, история отчётов. |

## Базовый набор правил

Правила применяются к **линиям** сертификатов — хронологическим цепочкам выпусков на один набор имён, а не к отдельным записям CT. Без этой группировки счётчики в сводке завышаются на порядок.

**Находки:**

- актуальный сертификат линии истёк и не был перевыпущен;
- истекает менее чем через 7 / 30 дней;
- длина ключа RSA менее 2048;
- алгоритм подписи SHA-1 или слабее;
- wildcard-сертификат покрывает большое число имён;
- один публичный ключ в сертификатах на несвязанные имена;
- имя резолвится, но актуальный сертификат линии истёк;
- имя из SAN не резолвится вообще;
- имена тестовых, отладочных и служебных сред, засветившиеся в публичном логе;
- выпуск не атрибутирован — источник не связывается ни с инфраструктурным провайдером, ни с известным процессом компании.

**Информационные наблюдения** (факт в сводке, не находка): выпуск, атрибутируемый CDN/хостингу/PaaS · число УЦ с одновременно действующими сертификатами · медианный ритм продления.

Бесплатный ACME-УЦ сам по себе находкой не является: на современном периметре это норма, а не теневое ИТ. Находка — невозможность атрибутировать выпуск.

Полное описание — в [требованиях](docs/requirements-and-plan.md#24-движок-правил).

## Критерии приёмки PoC

Разведены на два контура — то, что проверяется на второй день, и то, что измеряется неделями.

**Контур A — «прототип работает» (день 2):** отчёты по 10 доменам целевого сегмента · полнота и доля ложных срабатываний посчитаны на калибровочных доменах · не более 20% записей снято оператором вручную · генерация до 10 минут · продакт запускает отчёт сам.

**Контур B — «гипотеза подтвердилась» (4–6 недель):** 10 отчётов передано · отклик сопоставлен с контрольной группой обычных писем · минимум на 2 встречах заказчик подтвердил, что часть найденного не учитывал · возражения зафиксированы.

Полностью — в [постановке](docs/poc.md#критерии-приёмки-poc).

## Калибровка

Точность инструмента измеряется на **собственных доменах группы** — Рутокен, Гардант, Актив, — где эталонный реестр известен. Там считаются полнота и ложные срабатывания, и оттуда же берётся обучающая выборка для фильтра принадлежности.

Продуктовую гипотезу собственные домены не проверяют: Актив — вендор PKI, его дисциплина выпуска заведомо выше средней по сегменту. Для гипотезы нужна компания из базы контактов, готовая сверить находки со своим учётом.

## Глоссарий

| Термин | Значение |
|---|---|
| **CT (Certificate Transparency)** | Публичные append-only логи, куда УЦ обязаны публиковать выпускаемые сертификаты. Удалить запись из лога нельзя. |
| **SAN (Subject Alternative Name)** | Список доменных имён, покрываемых сертификатом. Основной источник имён для отчёта. |
| **Предсертификат** | Технический объект, публикуемый в CT до выпуска конечного сертификата. Требует схлопывания, иначе объём удваивается. |
| **CLM (Certificate Lifecycle Management)** | Управление жизненным циклом сертификатов. Класс продуктов, к которому относится Рутокен CLM. |
| **Отпечаток публичного ключа** | Хеш публичного ключа. На нём строится правило «один ключ на несвязанных именах». |
| **Wildcard-сертификат** | Сертификат вида `*.example.com`. Один приватный ключ обслуживает произвольное число хостов. |
| **Линия сертификата** | Хронологическая цепочка выпусков на один и тот же набор имён. Единица счёта в отчёте — линии, а не записи CT. |
| **ACME** | Протокол автоматического выпуска сертификатов. На внешнем периметре — норма, встроенная в хостинг-панели, CDN и PaaS. |
